## 第 2 步　更新 `sitemap.xml` 的 `<lastmod>`（T-08）

**触发条件**：本次确实改动了页面时才做。没有改页面就跳过本步。

```bash
cd C:/Users/weibi/weibinlawyer-pages-internal/site-tools
"$PY" update_sitemap_lastmod.py            # dry-run：只处理工作区已改动的页面
"$PY" update_sitemap_lastmod.py --all      # dry-run：全量纠偏（一次性用）
"$PY" update_sitemap_lastmod.py --all --write   # 确认无误后落盘
"$PY" update_sitemap_lastmod.py --check    # 卡口：退出码 0 才可继续
"$PY" audit_sitemap_lastmod.py             # 独立稽核：期望 STALE=0
```

- [ ] 先 dry-run，确认「需改动」列表与本次实际改动的页面**一致**。
- [ ] 落盘后 `git diff sitemap.xml` **只有 `<lastmod>` 行变化**，条数不变。
- [ ] `--check` 退出码 **0**；`audit_sitemap_lastmod.py` 输出 `STALE=0`。

**铁律：`lastmod` 必须是该页面「真实的最后修改日期」。**
不得把整站批量刷成「今天」——大面积伪更新会降低搜索引擎对本站的信任度。
工具取值优先级（已固化在脚本里，不需要手改常量）：

1. 该文件在工作区**有未提交改动** → 用当天日期（它此刻正在被改）；
2. 该文件**已提交** → `git log -1 --format=%as -- <path>`；
3. **无法确定** → 不改动，列入「未处理」并单独报告。

> 历史教训（I-5）：旧版工具把日期写成常量 `NEWDATE = '2026-09-11'`，
> 无论哪天运行都盖同一个日期，直接造成 `lastmod` 与实际修改时间脱节。
> 旧版已改名为 `update_sitemap_lastmod.legacy-20260912.py` 留档，**勿再回退**。

## 第 4 步　行尾符检查（Windows 专用）

本仓库 `core.autocrlf=true`，工作区文件应为 **CRLF**。

- [ ] 任何批量改写脚本必须**保留原行尾**，不得整份转成 LF。
- [ ] 提交前 `git diff` 只出现预期改动行；若出现 `LF will be replaced by CRLF` 警告，需查明是哪一步改写了行尾。

> 历史教训：用 `io.open(path,"w")` 且未指定 `newline=""` 重写整份 XML，会把 CRLF 悄悄转成 LF。
> `git diff` 看不到（autocrlf 双向归一会抵消），但**整份文件的行尾已被改动**，属未声明的副作用。
